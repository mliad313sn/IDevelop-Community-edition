# Security audit — IDevelop Community Edition

- **Date:** 2026-09-29
- **Codebase:** branch `claude/friendly-hawking-9iv6qf` at `e00b25a`, audited and fixed on a worktree branch
- **Auditor:** internal white-box review (source code, configuration, dependencies, container files). This was **not** an external penetration test.

## Scope

Server (`server.js`, `src/**`), views (`views/**`, including the inline scripts), browser code (`public/js/**`), SQL migrations where relevant, `Dockerfile`, `docker-compose.yml`, `package.json` / `package-lock.json`, and a read of the Windows installer defaults.

The review covered these areas:

1. injection (SQL, command/path, template, stored and reflected XSS);
2. authentication (sessions, passwords, lockout, MFA, password reset, SSO, SCIM and API keys);
3. authorisation (IDOR on `:id` routes, employee self-service, the routes added in this release);
4. CSRF;
5. headers and transport;
6. SSRF;
7. files (uploads, downloads, formula injection, zip bombs);
8. secrets and cryptography;
9. denial of service;
10. dependencies;
11. container and installer defaults.

Out of scope: the `mobile/` client, the infrastructure the product is deployed on, and dynamic testing against a running instance beyond the Jest suite.

## Methodology

- **Route inventory.** Every `router.(get|post|put|patch|delete)` and every mounted router was listed, the guard in front of each was checked, and the routes reachable without a session were listed (see "Unauthenticated surface").
- **Pattern search, then manual reading.** We searched for:
    - string-built SQL (`${…}` inside `db.*` calls, `ORDER BY ${…}`);
    - raw EJS output (`<%-`) and `innerHTML` / `insertAdjacentHTML`;
    - `child_process`, `Math.random`, outbound HTTP (`fetch`, `http(s).request`);
    - `sendFile` / `download`, `multer`, and `xlsx.readFile/load`;
    - role checks (`role === 'superadmin'`) and Referer-based redirects.

    Each hit was read in context and classified as a vulnerability, a hardening gap or a false positive.

- **Recent changes.** The feature commits in this release (`b2d1dcc`, `538f60d`, `f5310b5`, `22ac6ee`, `6455b02`) were reviewed diff by diff: `/employee/my-data`, `/compliance/register`, `/api/self-assessment/team/approve-all`, recognition, growth panels, and Slack/Teams webhooks.
- **Dependencies.** We ran `npm audit` and `npm audit --omit=dev`, read the advisories, and read the upstream changelog before any major upgrade.
- **Regression tests.** Every fix has a Jest test in `tests/unit/securityAudit20260929.test.js`: one `describe` block per finding id. The full suite ran against a freshly migrated and seeded PostgreSQL database.

Severity is qualitative in the CVSS style (Critical / High / Medium / Low / Info). It weighs the privileges an attacker needs, the reach of the impact, and the existing mitigations.

## Existing controls verified

These were read in the source and, where noted, exercised by the existing tests. They were not assumed.

**Session**

- Cookie `httpOnly`, `SameSite=Lax`, and `Secure` set to `auto`. A boot guard fails when `COOKIE_SECURE` is on without `TRUST_PROXY` (`server.js:285-345`).
- Neutral cookie name, and secret rotation through a comma-separated `SESSION_SECRET`.
- `req.session.regenerate` on password, MFA and SSO sign-in (`src/controllers/AuthController.js:483,505,745`; `src/controllers/SsoController.js:556,596,711`).
- Logout is POST-only and destroys the session (`src/routes/index.js:260`, `AuthController.js:816-836`).
- Idle timeout (60 min) and absolute cap (24 h) (`src/middleware/sessionActivity.js:18-24`).
- No session row for an anonymous visitor outside the form pages, and shared-computer mode (opt-in) with tab-close sign-out (`anonymousNoSession.test.js`, `sharedComputerMode.test.js`).
- `Cache-Control: no-store` on dynamic responses.

**Passwords**

- bcrypt (cost 10), minimum 12 and maximum 128 characters, with sequence and repeat rules (`src/utils/passwordValidator.js:69-75`) and password history.
- Constant-work anti-enumeration on sign-in (`src/middleware/auth.js:12-50`).
- Account lockout and login rate limit (`server.js:784-787`, `src/middleware/rateLimiter.js`).

**MFA**

- TOTP with window 1. Each accepted code is **consumed**: a unique index blocks replay (`src/services/MfaService.js:286-305`).
- 10 single-use backup codes, 40-bit random, bcrypt-hashed (`MfaService.js:317-350`).
- The pending MFA sign-in is invalidated after 5 wrong codes (`AuthController.js:605-607`).

**Password reset**

- 256-bit token, stored as SHA-256 and looked up by hash, so no timing oracle (`src/services/PasswordResetService.js:131-136`).
- Short TTL; single use through an atomic `UPDATE … WHERE used_at IS NULL AND expires_at > now()` (`:209`).
- Other tokens are invalidated, and sessions are revoked on reset.

**SSO**

- OIDC uses the authorization-code flow with PKCE S256, `state` and `nonce`, stored in the session and single-use (`src/config/sso.js:468-514`).
- SAML (`sso.js:782-802`):
    - `wantAssertionsSigned`, `wantAuthnResponseSigned` (default on), audience set to our issuer, sha256;
    - `validateInResponseTo: 'always'` for SP-initiated flows, with a request cache;
    - 3-minute clock skew.
- The Entra bearer token is pinned to RS256 with issuer, audience and tenant checks (`sso.js:556-590`).
- IdP metadata fetch: https only, DNS-checked, connection pinned, no redirects, size and time caps (`src/services/SamlMetadataService.js:295-370`).

**API keys and SCIM**

- 192-bit `ak_` keys, stored as SHA-256 and looked up by hash (`src/services/ApiKeyService.js:18,97`).
- Per-feed scope allow-lists (`src/middleware/apiAuth.js:47-84`); SCIM writes need a write scope.
- Keys are scoped to the owner admin's RBAC profile.
- The legacy shared key is compared with `timingSafeEqual` and is never `APP_KEY`.

**CSRF**

- `csrf-sync` synchroniser token on form posts (`server.js:593-660`).
- Same-origin guard for every unsafe method (`server.js:501-586`). `X-Forwarded-Host` is trusted only behind `TRUST_PROXY`.

**Headers**

- helmet CSP with a per-request script nonce, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'self'` and `form-action 'self'` (`server.js:114-139`).
- `nosniff`, `Referrer-Policy: no-referrer` and `X-Frame-Options: SAMEORIGIN` (helmet defaults, checked by request).
- HSTS on HTTPS responses only (`server.js:142`).
- `trust proxy` off by default (`server.js:73`).

**Host header**

- E-mail links never use the Host header: `APP_BASE_URL`, else an exact-match `TRUSTED_HOSTS` list (`src/utils/emailTemplate.js:90-125`).
- The HTTP→HTTPS redirect reduces Host to a bare hostname (`src/utils/tlsServer.js:77-95`).

**SQL**

- Parameterised queries throughout.
- `ORDER BY` goes through `sortClause` with a whitelist (`src/utils/listTools.js:93-102`).

**Files**

- Upload type and size limits on every multer instance, each built with `preservePath` so the guard sees the client file name as sent (a folder path, a control character or more than 200 characters is refused).

The previous Unix-socket-only scan left every upload of a Windows install in `scan_error`. ### Excluded as false positives (`query-filters`)

- **`js/missing-token-validation`** (`server.js`, express-session middleware). CodeQL reports a cookie middleware unless it sees `csurf`, `lusca` or fastify-csrf. This app uses **csrf-sync**: a synchroniser token in the session, mounted with `app.use` in `server.js` before the `/api/v1` and `/` routers. Every unsafe-method route is registered after it. `app.post('/logout')` and `app.post('/login')` come after it too, and the only `app.use` mounts before it are body parsers, static files, health probes and the session itself. `httpHardening.csrfSkip` exempts four cases:
    - `/api/*`: API key, bearer token or session JSON, all behind the origin guard;
    - `POST /login`: the origin guard refuses a cross-origin Origin;
    - IdP callbacks: protected by state or assertion signatures;
    - JSON bodies: they need CORS cross-site, and `originGuard` refuses a JSON mutation without a matching Origin or a validated credential.

    `tests/unit/csrfMultipart.test.js` enumerates every multipart mount and checks that it is CSRF-checked. The rule has no other use in this code base (one cookie middleware), so the whole rule is excluded rather than one alert. The second alert was in that test file and is covered by `paths-ignore: tests/**`.

- **`js/insufficient-password-hash`** (`src/services/ApiKeyService.js:18`, `src/middleware/rateLimiter.js` `validatedKeyId`). Both hash an **API key**, not a password. Keys are `'ak_' + crypto.randomBytes(24)`, which is 192 bits from the CSPRNG. For a key with that much entropy, an unsalted SHA-256 lookup hash is the standard construction: brute force is infeasible and a slow KDF would add CPU cost to every API call. `validatedKeyId` only keys an in-memory cache. Passwords are hashed with bcrypt everywhere (auth, employee auth, onboarding, reset). Switching to HMAC-SHA256 with a server key would not clear the alert (CodeQL models `createHmac` the same way), and it would invalidate every stored `api_keys.key_hash` without a migration. **Compensating control:** a Jest guard fails if any `createHash` or `createHmac` chain in `src/`, `scripts/` or `server.js` mentions a password-like identifier.

### Path exclusion

- `paths-ignore: tests/**`: Jest suites deliberately build bare Express apps without limiters, fake multipart uploads and weak inputs to exercise the guards. This covers the 3 `js/missing-rate-limiting` alerts and the `js/missing-token-validation` alert in tests. The existing ignores remain: `node_modules`, `public/vendor`, `coverage` and `*.min.js`.

### Accepted by design (high, dismissed as « won't fix »): the SQL console

- **`js/sql-injection`** (`src/services/SqlConsoleService.js`, the transactional and autocommit `client.query` calls). The SQL console exists to run the operator's own SQL, so the query string is user-controlled on purpose; no sanitiser can change that. The risk is carried by the controls around it, not by the query:
    - off unless the operator sets `SQL_CONSOLE_ENABLED=1` (separation of duties);
    - super-admin only;
    - pure reads run under the restricted `sqlconsole_reader` role (migration 167), which cannot read secret columns;
    - writes are refused against the append-only audit tables and anything built on them (`_auditTamperViolation`), and secret relations are refused for read and write;
    - every run is written to the audit trail with its SQL (capped at 4 000 characters).

    A maintainer dismisses these two alerts as « won't fix » in code scanning, with a link to this section. A rule-wide exclusion would also hide a real injection elsewhere, so the rule stays on.

### Accepted by design (high, dismissed as « won't fix »): the first-run password

- **`js/clear-text-logging`** (`src/services/AuthService.js`, the first-run banner). On a brand-new install with no `BOOTSTRAP_ADMIN_PASSWORD` set, the app generates a random SuperAdmin password and prints it once to the server console, because that console is the only channel the installer has. The controls:
    - printed only when the password was generated, never when the operator supplied one;
    - printed once, on the run that creates the account, and never again;
    - the account must change it at first sign-in (`forcePasswordChange`), so the printed value is good for exactly one sign-in.

    A maintainer dismisses this alert as « won't fix » with a link to this section.

### Accepted (alert left open, medium)

- **`js/sensitive-get-query`** (`src/middleware/apiAuth.js` `presentedApiKey`, `src/api/v1/index.js` `discoveryAllowed`). The `?apiKey=` query parameter is a deliberate legacy path for Power BI `Web.Contents` feeds. It is honoured only for a key that carries the per-key `allow_query_key` flag (migration 163, off by default for new keys), or for the env shared key with `API_KEY_QUERY_STRING=1`. Any other key in the URL is refused with `api_key_in_url_refused`. `discoveryAllowed` only tests that a credential is present. Moving the key out of `req.query` without dropping the flag would just hide the same data flow, so the alert stays visible as the record of this accepted risk. It is a medium (warning) alert and does not fail the check. Retire the flag once the last legacy feed sends `X-API-Key`.

## Residual risks and recommendations

1. **External penetration test before GA.** This review was white-box and in-house. Commission an independent web-application test (authenticated, multi-role) and a configuration review of a production-like install (TLS termination, reverse proxy, `TRUST_PROXY`, backups).
2. **Coordinated disclosure and bug bounty.** Keep `SECURITY.md` current. Consider a bounty (even a modest or private one) after GA.
3. **CSP (SA-14), done.** Inline `on*=` handlers are gone and `script-src-attr` is `'none'`, so a future HTML-injection bug cannot run an event handler. What remains is `style-src 'unsafe-inline'` for inline `style=` attributes: a lower-risk, separate migration.
4. **i18next `escapeValue:false`.** Every `<%- __(key, {…})` with request- or database-derived values must escape those values, as the SA-02 fix does. A lint rule or a helper (`__html(key, values)` that escapes the values) would make this systematic.
5. **CSRF on multipart routes (SA-15), done.** Every upload presents the synchroniser token (header, or `?_csrf=` on a native multipart form) and a missing or wrong token is refused with 403.
6. **LMS and xAPI outbound calls** are still made with `fetch` and are not pinned (the copilot now is, see SA-17). The base-URL guards cover IP-literal spellings, but a DNS name that resolves to loopback or metadata is only caught for webhooks, SAML metadata, the safety-gate webhook and the copilot. Route every outbound integration call through one pinned HTTP helper.
7. **Container (SA-16).** Keep the code root-owned and read-only, and mount `uploads/`, `tmp/`, `logs/` and `backups/` as volumes.
8. **`APP_KEY` (SA-18).** Done: a missing or weak `APP_KEY` is fatal in production, and `SESSION_SECRET` is no longer an encryption key there (secretBox v2). Operators upgrading must set a strong `APP_KEY` (rotate with `scripts/rotate-app-key.js`).
9. **Dependency hygiene.** Add `npm audit --omit=dev` (fail on high) to CI, and review deprecated packages, not only advisories.
10. **Audit log (SA-29, SA-30).** The row hash includes `created_at` as text, so the verifier must run with the database's time zone setting unchanged; set `timezone` once, at install. The failed-sign-in fingerprint is keyed with `SESSION_SECRET`: rotating it changes the fingerprint of the same identifier from then on. With the installer's audit-owner separation, the redaction and purge functions must be owned by the audit owner role; until the installer does it, an erasure fails closed on such an install.
11. **Privacy and shared devices (SA-32 to SA-35).** The tab-close sign-out of shared-computer mode is best-effort (a browser may not send the beacon); the short idle window is the backstop, so keep `kioskIdleMinutes` low. Consent texts are versioned (`dei-consent-v1`): bump the version whenever the wording of the consent changes. Diversity values that pre-date consent stay set aside until the person confirms them or HR clears them.
12. **Mail privacy (SA-37, SA-38).** A set-password link is a credential for 72 hours: the configured base URL (`appBaseUrl` or `APP_BASE_URL`) must be the public HTTPS address, and the outgoing mail server must use TLS. After the upgrade, a schedule that sent to typed addresses stays suspended until its owner chooses accounts; tell report owners before upgrading. A report copy is readable in the application until it is emptied, so keep `reportRunRetentionDays` as short as the business allows.
13. **Backup keys (SA-39).** A backup whose key is lost is lost. On Windows, export the recovery copy of the backup key once, at installation (`node scripts/backup-key.js export --out <file>`), and keep it offline: a DPAPI key does not leave its machine. On Linux and Docker the key is derived from `APP_KEY`: keep `APP_KEY` offline, apart from the backups, change it only with `scripts/rotate-app-key.js`, and keep the previous value too (`backup-key.js import-app-key` restores access if the keyring is lost or `APP_KEY` was changed by hand). Anyone holding the `.env` of a Linux or Docker install can decrypt its backups. The Docker image ships no `pg_dump`; see `docs/BACKUPS.md`. The file and keyring formats (`IDVBKENC`, the DPAPI entropy, the derived salt) are frozen: a change needs a new format version, never an edit.
14. **Safety-gate waivers (SA-40).** A waiver lets a person through the gate for up to 72 hours although the data says they are not cleared. Review the running waivers (« Authorised by waiver » on the safety clearances page) and the `SAFETY_GATE_WAIVER_*` audit lines regularly, mark every rule that the law makes mandatory as such, and tell access-control integrators that WAIVED is reported with `cleared: true`, `waived: true` and `waiverExpiresAt`: a system that must refuse waived people has to read the `waived` flag.
15. **9-box reasons (SA-41).** A reason for a box change is free text about a person. Tell the people who write them that they are part of the person's file: returned on a formal access request and erased with the person. Placements decided before this release are shown as « rebuilt from history » with no reason: none was ever asked for, and none is invented.
16. **Workflow authority and resets (SA-42).** Callers of the former `/v2/talent` rating and placement writes now get 410: move any integration to the 9-box console. Supervisors no longer act on performance improvement plans; tell managers that a plan is proposed, activated and closed by the person's direct manager or an administrator who covers them. The SuperAdmin reset reopens work that was already decided: review the `MAINT_RESET_ASSESSMENT` audit lines and the `assessment_reset` movements with the rest of the maintenance overrides.
17. **Reasons on decisions (SA-43).** The reasons written when a successor is removed, an absence cancelled, a rule deactivated or an uplift declined are part of the record. The ones about a person are returned on a formal access request and replaced by `[erased]` on erasure; tell the people who write them so. Successors, rules and absences removed before this release were deleted and cannot be recovered.
18. **Upload antivirus (SA-45).** Install a scanner (ClamAV, or keep Microsoft Defender's real-time protection on Windows): without one, uploads are accepted and marked not scanned, which the health page and the `UPLOAD_NOT_SCANNED` audit lines show. With `requireMalwareScan` set to true (or `auto` once a scanner is detected), a failing scanner refuses every upload until it answers again. The scan adds about 0.5 to 3 seconds per file.
19. **Escaping inventories (SA-46).** A new raw output, client HTML sink or data in an inline script fails `rawOutputInventory.test.js` until it is reviewed: review the source of the value before raising a count, and pass data to a script through `views/partials/json-script.ejs`.
