# OWASP ASVS 4.0.3 — Level 2 self-assessment

- **Product:** IDevelop Community Edition (Node.js / Express 4, server-rendered EJS, PostgreSQL)
- **Standard:** [OWASP Application Security Verification Standard 4.0.3](https://owasp.org/www-project-application-security-verification-standard/), Level 2 (every L1 and L2 requirement)
- **Date:** 2026-09-30
- **Method:** white-box verification in the source code, backed by the Jest suite. Each row cites the code (`file:line` where a line is useful) or the test that proves it. It builds on the internal audit in [`SECURITY-AUDIT.md`](SECURITY-AUDIT.md) and does not repeat its findings.
- **Nature:** this is a **self-assessment by the development team, not a certification** and not a third-party verification. See [`COMPLIANCE-MAPPING.md`](COMPLIANCE-MAPPING.md) for what a deploying organisation still has to do.

## Status legend

| Status           | Meaning                                                                                                                           |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Pass**         | The requirement is met by the code as it was before this assessment; the evidence was read, and a test exists where one is cited. |
| **Fixed**        | A gap found during this assessment and closed on this branch, with a regression test.                                             |
| **Partial**      | Met in part, or met only with a deployment setting; the notes say what is missing.                                                |
| **Gap**          | Not met. The notes say why it was not fixed here.                                                                                 |
| **N/A**          | The feature the requirement is about does not exist in the product.                                                               |
| **Not verified** | We could not verify it from the code and tests alone (process, infrastructure or run-time behaviour).                             |

### Password list (2.1.7)

No list of breached passwords with a clearly public-domain or CC0 licence could be obtained offline in this environment (the well-known "top 10k" lists are MIT- or CC-BY-licensed). The bundled list `src/data/common-passwords.txt` was therefore **generated for this project** from well-known patterns: the most common base words of published password studies (English and French), keyboard walks, digit runs, and product- and season-specific words. The file is original work under the project licence (see `NOTICE`). The validator also removes case, common leetspeak substitutions and leading or trailing digits and symbols before the lookup, so `Sunshine2024!` or `P@ssw0rd123456` are caught by the base words `sunshine` and `password`. An operator can append entries (one per line) or replace the file with a larger licensed list.

## Hardening beyond ASVS 4.0.3 (done in this branch)

These are not ASVS 4.0.3 requirements, but they are asked for by the OWASP Secure Headers Project and ASVS 5.0 drafts:

- `Permissions-Policy` denies camera, microphone, geolocation, payment, USB, serial, HID, MIDI, sensors and screen capture (`server.js`, `asvsHeaders.test.js`).
- `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin` are pinned explicitly rather than left to library defaults.
- `autocomplete="username"` / `current-password` on the sign-in form and `new-password` on the signup form, so password managers fill the right field (ASVS 5.0 V6).
- API key events created from `/api/v1/admin/api-keys` now carry the real actor, IP and request id.

## Gaps left open, and why

| ID            | Reason                                                                                                                  |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 2.3.2         | WebAuthn / FIDO2 is a new authenticator type (enrolment, storage, recovery), a feature rather than a contained fix.     |
| 2.4.5         | A pepper needs a hash migration and a key custody decision.                                                             |
| 3.3.2         | Tightening the idle and absolute defaults changes every user's experience; it is an operator setting and is documented. |
| 3.4.4         | `__Host-` requires HTTPS everywhere; plain-HTTP LAN installs are still supported.                                       |
| 5.3.3, 14.4.3 | Removing `script-src-attr 'unsafe-inline'` requires moving every inline handler in the views (SA-14).                   |
| 2.2.3, 2.5.5  | Notifying users of password and MFA changes needs a new e-mail template and a decision on SSO-only accounts.            |
